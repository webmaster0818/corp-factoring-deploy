# テクニカルSEO 学習ノート

## Core Web Vitals (2020年〜)

**3つの主要指標:**
1. **LCP (Largest Contentful Paint)** - 最大コンテンツの描画時間
2. **FID (First Input Delay)** - 初回入力遅延
3. **CLS (Cumulative Layout Shift)** - 累積レイアウトシフト

**重要ポイント:**
- 2021年以降、ランキング要因に
- ページ単位で評価(サイト単位ではない)
- **コンテンツ品質が最優先**、Core Web Vitalsは補助的要因
- AMPは自動的にCore Web Vitalsに最適化

**評価方法:**
- Search Consoleの「ウェブに関する主な指標」レポート
- PageSpeed Insights
- Chrome拡張機能
- CrUXデータ

**改善方法:**
- LCP: サーバー応答時間、リソースロード時間、クライアントサイドレンダリング
- FID: JavaScriptの実行時間削減、コード分割
- CLS: 画像・動画サイズ指定、広告スロット予約

**真実:**
- 極端に悪くない限りランキングに大きな影響なし
- 関連性が等しい場合、Core Web Vitalsが決定打に
- 指標は時代とともに変化する可能性あり

## ページ削除・noindex

**404 vs 410 vs noindex:**
- **404** - ページが見つからない(一時的)
- **410** - ページが永久に削除された(404より若干速い)
- **noindex** - インデックスから除外(404より若干速い)
- **結論:** 中長期的には差はない。どれでも使える

**JavaScript noindex:**
- クライアントサイドでnoindex挿入は可能
- しかし**推奨されない**(処理に時間がかかる)
- セカンドウェーブのインデックスになる

**削除速度:**
- 410とnoindexは404より若干速い
- しかし実質的な差は小さい
- Search Consoleの「URL削除ツール」が最速

## モバイルファーストインデックス (2018年〜)

**よくある誤解:**
- モバイル版がないとインデックスされない → ✗ 誤り
- PCサイトだけでもインデックスされる
- ただしモバイル版の内容で評価される

**レスポンシブWebデザイン:**
- Google推奨の方式
- 同じHTML、CSSで表示を変える
- 別URLの管理不要

**動的配信・別URL:**
- モバイルとPCで異なるHTML配信
- Vary HTTPヘッダー必須
- canonical/alternateの正しい設定

**注意点:**
- モバイル版に全コンテンツがあるか確認
- 構造化データもモバイル版に
- CSS/JSのブロック解除

## 構造化データ (Schema.org)

**重要な種類:**
- **Article** - 記事
- **Product** - 商品
- **Recipe** - レシピ
- **Event** - イベント
- **FAQ** - よくある質問
- **How-to** - ハウツー
- **Video** - 動画
- **Review** - レビュー
- **LocalBusiness** - ローカルビジネス

**リッチリザルト:**
- 検索結果での視覚的な強化表示
- CTR向上に貢献
- レシピ、イベント、商品などで効果大

**実装方法:**
- JSON-LD(推奨)
- Microdata
- RDFa

**テストツール:**
- リッチリザルトテスト
- 構造化データテストツール(廃止予定)
- Search Consoleの構造化データレポート

**注意点:**
- スパム目的の構造化データは厳禁
- 実際のページコンテンツと一致させる
- 必須プロパティを満たす

## クロール・インデックス最適化

**robots.txt:**
- クロールの制御
- CSS/JSはブロックしない(重要!)
- 不要なページのクロール防止

**sitemap.xml:**
- 新規ページの発見促進
- 更新頻度の伝達
- 動的サイトマップ推奨

**新規サイトの発見:**
- **外部リンクがベスト**(最も確実)
- インデックス登録リクエストより確実性あり
- サイトマップも併用

**インデックス登録されない問題:**
- 技術的問題がなくてもインデックスされないことがある
- コンテンツ品質が原因の可能性
- クロールバジェットの問題
- 重複コンテンツ

## JavaScript SEO

**レンダリング:**
- Googlebotは JavaScript をレンダリングできる
- しかし「セカンドウェーブ」のインデックス
- 初回クロールではHTMLのみ

**推奨:**
- サーバーサイドレンダリング(SSR)
- 静的サイト生成(SSG)
- 重要コンテンツはHTMLに

**クライアントサイドレンダリング(CSR):**
- SEOには不利
- 可能な限り避ける
- どうしても必要なら動的レンダリング

## ページスピード最適化

**計測ツール:**
- PageSpeed Insights
- Lighthouse
- WebPageTest
- Chrome DevTools

**改善要素:**
1. **サーバー応答時間** - TTFB短縮
2. **リソース最適化** - 画像圧縮、CSS/JS最小化
3. **レンダリング** - クリティカルCSS、遅延読み込み
4. **キャッシュ** - ブラウザキャッシュ、CDN

**origin: コマンド:**
- PageSpeed Insightsでサイト全体の速度チェック
- 個別ページだけでなく全体を把握

## HTTPS

**必須要件:**
- 2014年からランキング要因
- HTTP/2の利用にも必須
- セキュリティの基本

**移行時の注意:**
- 301リダイレクト必須
- Search Consoleに別プロパティ登録
- canonical/hreflang更新
- 否認ファイル再アップロード

---

## 重複コンテンツ対策

**canonical タグ:**
- 正規URLの指定
- 重複ページの統合
- パラメータ付きURLの正規化

**使用例:**
- ページネーション
- ソート・フィルタ機能
- セッションID付きURL
- プリント用ページ

**注意:**
- rel="canonical"は"提案"であり"命令"ではない
- Googleが無視することもある

## リダイレクト

**301リダイレクト:**
- 恒久的な移転
- PageRankを引き継ぐ
- サイト移転時に必須

**302リダイレクト:**
- 一時的な移転
- PageRank引き継がない可能性

**処理時間:**
- PageRankの低いページは処理が遅い
- 大規模サイトは数週間〜数ヶ月かかることも

**チェーンリダイレクト:**
- 複数回のリダイレクトは避ける
- 最終URLへ直接リダイレクト

## AMP (Accelerated Mobile Pages)

**メリット:**
- 超高速表示
- Core Web Vitals自動最適化
- トップニュース掲載(ニュースサイト)

**デメリット:**
- 制約が多い
- JavaScript制限
- カスタマイズに限界

**2021年以降:**
- トップニュース掲載にAMP必須ではなくなった
- Core Web Vitals対応で代替可能
- しかし簡単確実な最適化手段として有効

**update-cache:**
- AMPキャッシュの強制更新
- update-pingは廃止

## XMLサイトマップ詳細

**含めるべきURL:**
- インデックスさせたいページ
- 定期更新されるページ
- 発見されにくい深い階層のページ

**含めないURL:**
- noindexページ(例外あり)
- 重複ページ
- リダイレクトページ
- エラーページ

**例外 - noindexページをサイトマップに:**
- インデックスから早急に削除したい場合
- クロールを促進して処理速度アップが目的
- 一時的な措置

**更新頻度:**
- 動的生成が理想
- 静的なら定期更新
- 大規模サイトは分割サイトマップ

## Search Console活用

**重要レポート:**
1. **検索パフォーマンス** - クエリ、ページ、国、デバイス
2. **カバレッジ** - インデックス状況
3. **ウェブに関する主な指標** - Core Web Vitals
4. **モバイルユーザビリティ** - モバイル対応状況
5. **構造化データ** - リッチリザルト対応

**Search Analytics API:**
- 16ヶ月分のデータ取得可能
- 独自レポート作成
- データ分析の自動化

## まとめ: テクニカルSEOの原則

1. **Googlebotがアクセスできること**
2. **レンダリングできること**
3. **インデックスできること**
4. **高速に表示できること**
5. **モバイルで使いやすいこと**

テクニカルSEOは基盤。コンテンツという建物を支える土台。
土台がしっかりしていないと、どんなに良いコンテンツも評価されない。
